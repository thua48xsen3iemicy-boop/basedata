# State machine, role handoff и ограничение параллельности

**Цель:** разные модели и добровольцы должны иметь одинаковый воспроизводимый рабочий процесс, не передавая полную переписку друг другу. Это контракт **артефактов**, а не уже работающий автоматический оркестратор.

## 1. Два независимых состояния

`WorkOrder.status`: `proposed → assigned → in_progress → review → done`, со специальными `blocked` и `example_only`. `done` означает завершение задачи в git, **не** утверждение знаний.

`KnowledgeUnit.status` / `AssessmentItem.status`: `draft → machine_reviewed → expert_approved → published`, плюс `deprecated` с отдельным решением. В прототипе валидатор намеренно запрещает `expert_approved`/`published`, так как независимого журнала согласования ещё нет. `machine_reviewed` обозначает только записанный машинный отзыв, не доказательство корректности.

Точки возврата: review обнаружил ошибку → исправление по *новой малой задаче* или возврат order в работу; несовместимые источники → `blocked`; критическая нормативная неопределённость → human expert. Не путать состояние контентной сущности и статус PR.

## 2. Контрольный протокол одной задачи

1. **Постановка**: заказ `work/orders/<ID>/order.yaml` с `scope.allowed_paths`, `scope.read_ids`, цель, критерии приёмки, роль и `next_role` (опциональные `depends_on`, `model_tier`).
2. **Назначение**: исполнитель видит только scoped контекст и может заявить `blocked`, если отсутствуют исходные источники или права.
3. **Исполнение**: изменяет только разрешённую область; недоказанные факты маркирует, не скрывает; не читает весь репозиторий.
4. **Handoff**: пишет отдельный `work/handoffs/<ID>/<role>.yaml`; пути относительные, содержится краткая claim-evidence matrix, diff refs, проверки и открытые вопросы.
5. **Рецензия**: следующий независимый исполнитель оценивает данные, а не просто повторяет автора. Формальные проверки остаются за кодом.
6. **PR / merge**: изменения схематически валидны, review findings разрешены или оформлены в отдельные задачи, нет скрытого самоутверждения.
7. **Публикация**: *другой*, пока не реализованный, протокол с журналом человеческого утверждения и неизменяемым manifest; обычный merge в main НЕ публикация.

## 3. Запреты и ownership

| Одновременно разрешено | Несовместимо без разделения/очереди |
|---|---|
| Создание `knowledge/networking/ipv4/cidr/` и `knowledge/linux/.../` | Два автора в `knowledge/networking/ipv4/cidr/canonical.md` |
| Исследование темы A и тесты темы B | Два автора разных вопросов в одном `questions.yaml` |
| Новый `work/orders/ID-A` и новый `ID-B` | Параллельные правки `contracts/unit.schema.json` |
| Независимое read-only ревью и работа автора в отдельном branch | Рецензент перезаписывает исходники до фиксации findings |

Общие файлы (`AGENTS.md`, схемы, CI, глобальные индексы) — отдельные инфраструктурные work orders; изменения контрактов требуют миграционного плана. Проверка конфликтов **до запуска агентов** зависит от планировщика задач; нынешний `validate.py` не может доказывать отсутствие одновременных редакторов в разных ветках.

## 4. Компактный пакет контекста

Минимальный пакет: `AGENTS.md`, ближайший `AGENTS.md` по пути, конкретный `order.yaml`, ровно нужные схемы, контентные ID + ближайшие prereqs, ссылки/доказательства из предыдущего handoff, целевой diff. Ссылки на источники — не команды агенту. При недостатке контекста агент выписывает недостающие ID и запрашивает их *точечно*.

**Важное ограничение:** не пытаться прочесть сразу все `tests/`, `knowledge/`, PR и нормативные документы. Время сильной модели лучше расходовать на архитектуру, сложные разногласия и качественное ревью, а не на чтение тысяч страниц.

## 5. Пример маршрута

`Architect(strong) → Researcher(small+search) → Author(small) → AssessmentDesigner(small/code) → MachineReviewer(strong) → Validator(code) → HumanExpert(person) → ReleaseManager(manifest)`.

Это последовательность логических функций. На практике некоторые этапы могут объединяться в одной сессии, **но независимая проверка и запрет self-approval остаются**. Не привязывайте контракт к одному провайдеру модели.

Схема handoff: `contracts/handoff.schema.json`. Фактический протокол допускает очередной handoff из роли `author`, затем отдельный `machine_reviewer.yaml` под тем же `<ID>`.
