# Архитектура и семантические границы

## Главный граф

`StandardRequirement (versioned) → Competency → LearningOutcome → KnowledgeUnit → AssessmentItem`

`LearningPath` выбирает результаты/единицы, учитывает `prerequisites`; `Curriculum` сопоставляет нормативные требования, дисциплины, часы, семестры и формы контроля. Между нормативом и знанием **нет прямого равенства**: связка через проверяемый результат и уровень освоения.

Обратный путь: анализ результатов (вне Git, обезличенно) → выявление затруднений → изменение объяснений/вопросов через PR → новая версия опубликованных материалов.

## Что является source of truth

| Сущность | Где | Как изменяется |
|---|---|---|
| Факт/каноническое объяснение | `knowledge/<domain>/<subject>/<unit>/` | Редко; только по новой проверке; ID стабилен |
| Затруднения, примеры | рядом с unit | По результатам обучения, после ревью |
| Вопросы и ключи | `assessments/<domain>/<subject>/<unit>/` | Чаще; link на outcome ID и версию знаний |
| Компетенции / outcomes | `competencies/` + `unit.yaml` | Версионируются; не выводятся из названия темы |
| Внешний норматив | `standards/<jurisdiction>/<family>/` | Импорт конкретной редакции, источник, дата, лицензия |
| Учебный план | `curricula/` | Ссылается на редакции нормативов и outcomes; часы проверяет код |
| Учебный маршрут | `learning-paths/` | Ссылки на outcomes/units, порядок, требования к проверке |
| Студенческий прогресс | внешняя защищённая БД/LMS | Никогда в git |

## Уникальность и изменения

- Stable ID не содержит версию или название дисциплины: `NET.IPV4.CIDR`; outcome `LO.NET.IPV4.CIDR.01`; question `Q.NET.IPV4.CIDR.001`.
- `revision` — **ревизия в git**, а не обещание неизменности; курс релизится по git tag/commit SHA и manifest. Не заменяйте один опубликованный пакет в процессе прохождения.
- Изменение смысла цели обучения требует нового outcome ID и явной миграции ссылок. Изменение объяснения при прежнем результате может оставлять ID.
- `prerequisites` должны ссылаться на известные единицы и образовывать ациклический граф (проверяются базовым валидатором).
- Большие файлы и сканы стандартов хранить за пределами репозитория или с осознанной стратегией LFS; ссылок и структурированного извлечения обычно достаточно.

## Сборка нормативной программы

1. Импортировать требования, фиксировать юрисдикцию, дату, источник и контрольную сумму оригинала.
2. Сопоставить требования с outcomes (включая уровень `know`/`apply`/`analyze`) и указать основания.
3. Найти непокрытые компетенции: это задачи на расширение базы, а не галлюцинация отсутствующего покрытия.
4. Собрать темы/дисциплины из ссылок на фундамент; назначить часы и виды деятельности при соблюдении ограничений.
5. Валидировать суммарные часы, зависимые требования, покрытие, обязательные блоки, семестры.
6. Отдать на содержательное и нормативное утверждение; только затем экспортировать шаблоны DOCX/XLSX/PDF.

**Одинаковое название ≠ одинаковый outcome**. «Знать IPv4» и «диагностировать проблемы адресации» — разные доказательства освоения.

## Адаптация и измерение

Студенту показывается только необходимая часть банка знаний: входная диагностика, обязательные результаты, дополнительные разъяснения при ошибках, периодическое повторение. Информация о реальных учащихся и детальные события обучения хранятся отдельно с правилами приватности и разграничения доступа; в git попадают только агрегированные и разрешённые выводы для улучшений.

## Boundaries

- Сейчас: specification-first monorepo + схемы + проверки + одна вертикальная цепочка.
- Позже: синхронизация с Moodle, приватный assessment runtime, генератор документов, адаптивный планировщик, анализ ошибок и UI.
- Не превращать `AGENTS.md` в мегапромпт. Root = инварианты; nested = правила конкретного каталога; длинные объяснения в `docs/`.
