# Первый исследовательский пакет: основы локальных сетей и маршрутов

Цель — подготовить проверяемые предложения правок, а не автоматически утвердить учебный текст.
Ветка постановки: `task/network-foundations-research`. Исполнителей запускает пользователь.
Под direct route понимается connected route; различия терминологии ОС должны быть явно описаны.
Динамическая маршрутизация полностью вне пакета.

## Раздача

Каждому исполнителю передать один `work/orders/<TASK-ID>/PROMPT.md` и доступ к репозиторию
на одном зафиксированном commit этой ветки. Commit получить командой `git rev-parse HEAD` после
фиксации пакета. Один исполнитель — один заказ — одна отдельная ветка и PR.
Все восемь исследований независимы и допускают параллельное выполнение: каталоги записи не пересекаются.
Соседний результат не является обязательным входом; вопросы на стыках оставить для общего ревью.

| Тема | Заказ |
|---|---|
| MAC-адреса | `TASK-NET-RESEARCH-MAC` |
| Ethernet | `TASK-NET-RESEARCH-ETHERNET` |
| ARP | `TASK-NET-RESEARCH-ARP` |
| Широковещательный домен | `TASK-NET-RESEARCH-BROADCAST` |
| IPv4-адрес | `TASK-NET-RESEARCH-IPV4` |
| Непосредственно подключённый маршрут (direct / connected) | `TASK-NET-RESEARCH-DIRECT` |

| Маршрут по умолчанию | `TASK-NET-RESEARCH-DEFAULT` |

## Контракт результатов

Существующие JSON Schema work-order и handoff используются без изменения.
Следующий формат исследовательских файлов — требования приёмки, а не новая машинная схема:
`tools/validate.py` не проверяет их полноту и достоверность; это задача рецензента.

- `sources.yaml`: список записей с `id`, `title`, `url`, `publisher`, `version`, `accessed_at`,
  `sections`, `document_status`, `updates`, `obsoleted_by`, `access_status`.
  Для неизвестного значения использовать null и пояснение в `notes`; не угадывать даты и номера разделов.
- `findings.md`: краткие основные принципы и таблица утверждений:
  локальный claim ID, формулировка, source ID + точный раздел, краткий пересказ доказательства,
  применимость/исключения, состояние supported/unresolved/conflicting.
  Разделять нормативное требование, объяснительную модель и поведение конкретной ОС.
  Для MUST/SHOULD/MAY сохранять контекст и силу требования; не превращать пример в общее правило.
- `proposals.md`: предлагаемые атомарные единицы и связи prerequisites, 2–4 измеримых outcomes,
  проверочные сценарии с ответами, типичные ошибки и точечные предложения правок по существующим путям/ID.
  Не переписывать существующий outcome с другим смыслом; новые ID отметить как кандидаты.
- `work/handoffs/<TASK-ID>/researcher.yaml`: реальная ветка, входы/выходы, основные claims с source_ids,
  фактические проверки, вопросы и `next_role: machine_reviewer`.
  `changed_paths` содержит только содержательные файлы внутри scope, не сам handoff.
  Handoff разрешён отдельным протоколом репозитория; заказ и общие файлы исполнитель не редактирует.

## Работа с источниками

RFC в brief — начальный список поиска, не готовая библиография доказанных утверждений.
Проверить RFC Editor metadata и влияющие Updates/Obsoletes по теме, не исследуя всю цепочку без необходимости.
Ethernet/MAC/bridging требуют IEEE 802.3, IEEE 802.1Q и официальных материалов IEEE Registration Authority;
RFC не заменяют эти стандарты. Если нужная редакция недоступна, указать пробел и доступный официальный материал,
не выдавать пересказ стороннего сайта за проверенный стандарт. Не копировать большие фрагменты стандартов.
Документация ОС допустима для connected/static route, но версия и граница применимости обязательны.

## Приёмка координатором

1. Сверить diff со scope, наличие всех результатов и валидность handoff: `python tools/validate.py`.
2. Независимый machine_reviewer проверяет ссылки, точные разделы, выводы, исключения и ответы сценариев.
3. Свести стыки: MAC/Ethernet/ARP, broadcast domain/subnet, route selection/next hop/ARP;
   устранить противоречия и дубли кандидатов ID. Вопросы без доказательств остаются открытыми.
4. На принятых исследованиях подготовить отдельные ограниченные author-заказы для knowledge/,
   затем assessment-заказы. Исследовательский PR сам по себе не меняет канонические знания.
5. Содержательное утверждение — за экспертом; machine review и структурный PASS его не заменяют.
