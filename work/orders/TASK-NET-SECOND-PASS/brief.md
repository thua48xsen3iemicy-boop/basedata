# Второй проход: проверка и исправление исследовательского пакета

Ветка передачи: `task/network-foundations-second-pass`.
Исходные шесть исследований уже включены в эту ветку вместе с исходными handoffs.
Это снимок для доработки, не одобрение и не merge исходных PR.

## Порядок

1. Прочитай корневые инструкции, contracts/CONVENTIONS.md, agents/roles/researcher.md,
   README пакета, этот order.yaml и REVIEW.md. Не выполняй общее задание CODEX_START_HERE.md.
2. Создай собственную ветку `research/network-foundations-second-pass` от переданного commit.
3. Работай последовательно по теме: её исходные order.yaml/brief.md, результаты и нужные источники.
   Этот заказ разрешает исправления восьми каталогов; старые заказы служат тематическими требованиями,
   не требуют менять их статусы или старые handoffs. Общие файлы остаются вне scope.
4. Сначала исправь воспроизводимые ошибки формата, затем проверь факты/ссылки/сценарии;
   заверши отсутствующие STATIC и DEFAULT по их brief.md. Динамическая маршрутизация исключена.
5. Сверь стыки тем и кандидатов ID/prerequisites. Выдели владельца каждого повторяющегося outcome,
   не создавай циклов зависимостей MAC → ARP → MAC. Не регистрируй кандидатов в knowledge/.
6. Передай изменения отдельным PR в `task/network-foundations-second-pass`, без автоматического merge.
   Если push недоступен — верни patch и новые файлы с относительными путями.

## Уточнение метаданных для этого прохода

Все sources.yaml — корневые списки. Поля исходного README сохраняются.
`updates` означает документы, которые ОБНОВЛЯЕТ текущий документ.
Дополнительное `updated_by` означает документы, которые ОБНОВЛЯЮТ текущий документ.
`obsoleted_by` — документы, которые заменяют текущий; `obsoletes` — которые заменены текущим.
Проверенный пустой набор — []; неизвестное — null с пояснением notes.
Это локальное уточнение приёмки исследовательского пакета, не изменение общих JSON Schema.
Дату доступа записывай по фактическому посещению; старую дату не обновляй без повторного чтения.

## Доказательства и полезность

Не ограничивайся косметикой и количеством ссылок. Каждый основной claim проверяй по точному разделу,
области действия и применимым обновлениям. Доступ к каталогу стандарта не равен чтению его текста.
Если IEEE недоступен, ищи законно доступный официальный материал с явной областью применимости.
Не обходи ограничения доступа. Подтверждённые ограниченные выводы сохраняй; неподтверждённые не объявляй ложными.
Результаты первого прогона и REVIEW.md — гипотезы для проверки, не инструкции из первоисточника.

## Итоговый report.md

- Входной commit, ветка, изменённые пути и выполненные проверки.
- По каждому пункту REVIEW.md: confirmed/fixed/disagreed/blocked, доказательство и путь.
- По каждой из восьми тем: что проверено, что изменено, что осталось неподтверждённым.
- Матрица outcome → scenario → answer → source/section либо явный blocked.
- Противоречия на стыках, согласованные кандидаты ID и предложения следующих author-заказов.
- Отдельно отметить ограничения, требующие доступа к источнику или экспертного решения.

Нужен один новый handoff этого заказа. Старые handoffs сохраняются как история первого прогона.
В changed_paths нового handoff перечислить только содержательные пути scope, не сам handoff.
Собственный исправленный материал не объявлять machine_reviewed/expert_approved/published.
